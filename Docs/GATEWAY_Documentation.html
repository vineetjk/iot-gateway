1. System Overview

The GATEWAY project is an STM32F103C8T6 (BluePill) based IoT gateway that reads industrial sensors via Modbus RTU (RS-485) and publishes telemetry data over MQTT using a 4G LTE cellular modem. It supports both SIMCom A7670C and Quectel EC200U modules through a compile-time hardware abstraction layer.

The system is designed for remote industrial monitoring where sensors (energy meters, temperature probes, PLCs) are connected via RS-485 and data must be transmitted to a cloud platform over cellular connectivity.

1.1 Key Features

  • Modbus RTU master with up to 32 configurable registers
  • Delta telemetry mode — only publishes changed values to save bandwidth
  • MQTT publish with QoS 1 over 4G LTE
  • Compile-time modem HAL supporting SIMCom and Quectel families
  • OTA firmware update via MQTT command + HTTPS download to external SPI flash
  • Serial firmware update via USB-C (bootloader + Python tool)
  • Ping-pong flash configuration with CRC32 validation
  • Full CLI interface over USB-C serial (115200 baud)
  • Alarm bit definitions with named alarm mappings
  • RGB LED status indication and heartbeat on built-in LED

3.3 GSM State Machine

The GSM connection is managed by a fully non-blocking state machine (gsm_sm.c) that is called from the main loop. It progresses through the following states:

IDLE --> RESET --> RESET_HOLD (200ms) --> BOOT_WAIT (6s, wait for "RDY")
  |
  +-> AT_PROBE (retry AT every 1s, 10s total)
  |
  +-> ECHO_OFF (ATE0)
  |
  +-> CMEE (AT+CMEE=2)
  |
  +-> SIM_CHECK (AT+CPIN?)
  |
  +-> NET_SEND / NET_RECV / NET_PAUSE (AT+CEREG? loop, 90s total)
  |
  +-> APN_SET (modem-specific APN command)
  |
  +-> PDP_ACT (activate PDP context) --> PDP_CHECK (fallback verify)
  |
  +-> MQTT_CLEANUP (vtable: close any stale sessions)
  |
  +-> MQTT_OPEN (vtable: connect to broker)
  |
  +-> MQTT_SUB (subscribe to command topic)
  |
  +-> CONNECTED
  |
  +-> ERROR (retry after timer)

4. Modem HAL

4.1 Compile-Time Modem Selection

Only one modem driver is compiled into the firmware at a time, saving approximately 2-4 KB flash and 350 bytes RAM. Selection is made in Core/Inc/modem_config.h:

/* Modem driver IDs */
#define MODEM_DRV_SIMCOM   0   /* SIMCom A7670C  -- AT+CMQTT, AT+HTTP */
#define MODEM_DRV_QUECTEL  1   /* Quectel EC200U -- AT+QMT, AT+QHTTP  */

/* SELECT YOUR MODEM HERE */
#define MODEM_DRIVER  MODEM_DRV_QUECTEL

To switch modems, change MODEM_DRIVER to the desired ID and rebuild the project. The preprocessor in modem_hal.h selects the correct vtable at compile time:

#if MODEM_DRIVER == MODEM_DRV_QUECTEL
  extern const ModemOps_t g_quectel_ops;
  #define MODEM_OPS  (&g_quectel_ops)
#elif MODEM_DRIVER == MODEM_DRV_SIMCOM
  extern const ModemOps_t g_simcom_ops;
  #define MODEM_OPS  (&g_simcom_ops)
#else
  #error "MODEM_DRIVER not set -- edit modem_config.h"
#endif

4.3 Adding a New Modem

  1. Create modem_<name>.c in App/01_Communication/
  2. Populate a const ModemOps_t struct with your implementations for all vtable fields
  3. Add a new #define MODEM_DRV_<NAME> ID in modem_config.h
  4. Add a corresponding #elif case in modem_hal.h that externs your ops struct and defines MODEM_OPS
  5. Implement all required vtable functions (MQTT connect/publish/disconnect/subscribe, HTTP get/range/download, SM steps)

5. OTA Update System

5.1 Overview

The OTA system allows remote firmware updates via MQTT command. The flow is:

  1. Device receives OTA command on MQTT subscription topic
  2. Application disconnects MQTT to free modem resources
  3. Downloads firmware binary via HTTPS (streaming to SPI flash)
  4. Verifies CRC32 of downloaded data against expected value
  5. Writes OTA metadata to SPI flash
  6. Sets SRAM magic flag and reboots into bootloader
  7. Bootloader reads metadata, copies firmware from SPI flash to internal flash
  8. Bootloader boots new firmware; application confirms boot via BL_ConfirmBoot()

5.4 Hosting Requirements

  • HTTPS required — firmware must be served over HTTPS for security
  • SIMCom A7670C: Uses native AT+HTTP* commands which support HTTPS directly
  • Quectel EC200U: AT+QHTTPGET is broken for HTTPS. Uses AT+QSSLOPEN to open a raw SSL/TLS socket and sends a manual HTTP GET request. The server must support HTTP/1.1 with Content-Length header.
  • GitHub Pages is recommended for hosting firmware binaries (free HTTPS, reliable CDN)
  • Binary must be served with correct Content-Length header
  • Server must support direct download (no redirects requiring JavaScript)

6.2 Flash Storage (Ping-Pong)

Configuration is stored in internal STM32 flash using two pages for wear levelling:

PageAddressSize
Config Page A0x0801E0002 KB
Config Page B0x0801E8002 KB

On save, the page with the lower write_count is erased and written with the new config (incremented write_count). On load, the page with the higher valid write_count is used. This provides:

  • Power-fail safety (one page always has valid data)
  • Wear levelling (alternating between pages)
  • CRC32 validation on read

6.4 Modbus Registers

Registers are configured via CLI commands. Each register definition specifies the slave address, register address, function code, data type, scaling factor, and a tag name used as the JSON key in telemetry messages.

Example CLI command to add a register:

reg add 1 0 3 0 0.1 voltage

This adds: slave 1, register address 0, function code 3 (holding), data type UINT16, scale 0.1, tag "voltage".

8. Build System

8.1 Debug Build

The default build configuration with full logging enabled:

  • Optimization: -O0 (no optimization, best for debugging)
  • DEBUG_LOG_ENABLED = 1 — all Debug_Printf/Debug_Print calls active
  • AT_LOG_ENABLED = 1 — AT command TX/RX logging active
  • Output: Debug/GATEWAY.bin

8.2 Release / Production Build

Steps to create a production build in STM32CubeIDE:

  1. Create Release Configuration: Project > Build Configurations > Manage > New, name "Release", copy from Debug
  2. Set Optimization: MCU GCC Compiler > Optimization > -Os (Optimize for size). Enable -ffunction-sections and -fdata-sections
  3. Add PRODUCTION Define: MCU GCC Compiler > Preprocessor > Add: PRODUCTION=1. Remove DEBUG if present.
  4. Enable LTO (optional): Add -flto to both Compiler and Linker miscellaneous flags (saves extra 2-5 KB)
  5. Linker GC: Ensure -Wl,--gc-sections is enabled (discard unused sections)
  6. Build: Set active config to Release, Clean, then Build All

9. Deployment

9.1 Serial Flashing

Method A: Python Tool (fw_update.py)

  1. Connect the device via USB-C (CH340 serial)
  2. Open a terminal, issue the fwupdate CLI command
  3. The device reboots into bootloader (sets SRAM flag 0x5E41A1FF at 0x20004FF8)
  4. Run on PC: python Tools/fw_update.py --port COMx --file Release/GATEWAY.bin
  5. The tool sends: SYNC byte (0x7F) > START command (with size + CRC) > DATA chunks (256 bytes each) > VERIFY command
  6. Bootloader ACKs each step, writes to internal flash, verifies CRC, then boots the application

Method B: STM32CubeIDE / ST-Link

Use Run > Debug (or Run) in STM32CubeIDE with ST-Link connected to SWD pins. This requires the SWD header to be accessible.

9.2 OTA Update Procedure

  1. Build the Release firmware binary (Release/GATEWAY.bin)
  2. Compute CRC32 of the binary: python -c "import binascii; print(hex(binascii.crc32(open('GATEWAY.bin','rb').read()) & 0xFFFFFFFF))"
  3. Upload the binary to an HTTPS-accessible URL (e.g., GitHub Pages)
  4. Publish OTA command to the device's MQTT command topic: 
    mosquitto_pub -h broker.emqx.io -t "delta/gw/XXXX/cmd" \
  -m "ota,https://yourusername.github.io/fw/gateway_v1.2.0.bin,55296,0xA1B2C3D4,1.2.0"
  5. Monitor device CLI output for download progress and reboot
  6. After reboot, device should reconnect to MQTT and call BL_ConfirmBoot()

9.3 GitHub Pages Hosting Setup

  1. Create a GitHub repository for firmware hosting (e.g., gateway-firmware)
  2. Enable GitHub Pages in repository Settings > Pages > Source: main branch
  3. Create a fw/ directory and upload firmware binaries
  4. The URL will be: https://<username>.github.io/gateway-firmware/fw/GATEWAY_v1.2.0.bin
  5. Optionally, create a manifest.json for automatic version checking: 
    {
  "latest_version": "1.2.0",
  "fw_url": "https://username.github.io/gateway-firmware/fw/GATEWAY_v1.2.0.bin",
  "fw_size": "55296",
  "fw_crc32": "0xA1B2C3D4"
}
Important: GitHub Pages serves files over HTTPS with proper Content-Length headers, making it suitable for both SIMCom (native HTTPS) and Quectel (SSL socket) download methods.

10. Troubleshooting

10.1 OLED Display Not Working

SymptomPossible CauseSolution
Display blank, no responseMissing I2C pull-up resistorsAdd 4.7k pull-ups on PB6 (SCL) and PB7 (SDA) to 3.3V
Display blank, i2cscan finds nothingWrong I2C address or wiring issueCheck wiring, try address 0x3D (some modules differ)
i2cscan finds 0x3C but display blankInitialization sequence issueCheck SSD1306 init timing, add delay after power-up

10.2 AT+QHTTPGET Broken for HTTPS (Quectel EC200U)

Problem: The Quectel EC200U AT+QHTTPGET command fails silently or returns error when the URL uses HTTPS. This is a known firmware limitation on certain EC200U versions.

Workaround: The firmware uses AT+QSSLOPEN to establish a raw SSL/TLS socket connection to the HTTPS server, then sends a manual HTTP GET request over the socket. The response is streamed and parsed for Content-Length and body data. This is implemented in Modem_HttpDownloadToFlash() for the Quectel driver.

10.3 Configuration Not Persisted to Flash

Problem: On first boot, Config_Init() loads defaults but does not call Config_Save(). This is intentional to avoid hanging if the flash pages at 0x0801E000 are not writable (some C8 chips have limited flash beyond 64 KB).

Solution:

  • After configuring via CLI, explicitly run save command
  • If save hangs or fails, the flash pages may not be accessible on your specific chip
  • Verify with uid command — check if flash size register reports 64 KB or 128 KB

10.4 GSM Module "RDY" URC Not Received

Problem: The A7670C sends "RDY" URC after boot, but the firmware sometimes misses it (UART not ready in time, or URC arrives during reset hold).

Solution: The state machine handles this gracefully — after the BOOT_WAIT timeout (6s), it falls through to AT_PROBE which sends "AT" every 1s for up to 10s. If the modem responds with "OK", connection proceeds normally.

10.5 AT+CPIN? Fails on First Try

Problem: SIM card is not ready immediately after modem boot. First AT+CPIN? returns ERROR.

Solution: The state machine has retry logic for SIM_CHECK state. If AT+CPIN? fails, it waits and retries. The SIM typically becomes ready within 2-5 seconds of modem boot.

10.6 Bootloader Not Yet Flashed

Problem: The bootloader is a separate project and must be flashed independently at address 0x08000000.

Solution:

  • Build the bootloader project separately
  • Flash bootloader to 0x08000000 using ST-Link
  • Flash application to 0x08003000
  • Without bootloader, the application must be linked at 0x08000000 (modify linker script ORIGIN)
